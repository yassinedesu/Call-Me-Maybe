Call Me Maybe · 7-day build plan

Force the model to speak valid JSON.

You're building a program that turns a natural-language prompt into a guaranteed-valid JSON function call — by intercepting the model's raw logits at each step and deleting every token that would break the required structure. A tiny 0.6B model becomes 100% reliable, by construction, not by luck.

What's actually graded

Two hard rules the whole subject is built on

Rule 01 · structure

Force validity mechanically

No prompting-and-hoping. If a reviewer sees you write "please output JSON" and parse the result, the core fails. Validity comes from masking logits — never from the prompt.

Rule 02 · choice

The model picks the function

No if "sum" in prompt heuristics. You decide what tokens are allowed; the model's probabilities decide which allowed token wins. That distinction is the skill.

Own these cold for the defense

The concepts a corrector will drill

Be able to say each one out loud. These are the mental model the whole build rests on.

01

Logits & greedy decoding

The model scores every vocab token as the next token. Greedy = take the highest — but you edit the scores first, then take argmax of what survives.

02

Autoregressive loop

Pick a token, append it, call the model again. Generation is one token at a time, always conditioned on everything so far. This loop is your whole program.

03

Byte-level BPE

Text becomes subword tokens. Qwen maps every raw byte to a printable stand-in — the space byte shows as Ġ. So "Ġsum" really means " sum".

04

The vocab file

vocab.json maps token-string → id. Invert it to answer the constant question: "if the model picks token X, which characters does it add?"

05

Constrained decoding = masking

Get logits → ask the validator which tokens are legal now → set illegal ones to -inf → argmax → append → repeat. Invalid output becomes unpickable.

06

The validator is a state machine

You know the exact shape, so no general parser. A trie for names, a small FSM for numbers, an FSM for strings, a set for booleans.

07

Two-stage design

Stage 1: force {"name":", constrain to the name trie. Stage 2: now you know the function, so force each fixed param name and constrain only the value by type.

08

Only call the model at decisions

Structural characters ({, :, ,, fixed param names) — you append those with no forward pass. Spend a model call only when it must genuinely choose. ~30 calls → ~5–10.

Clean separation earns points

Module responsibilities

Keep the grammar logic in one place, keyed by type — that's what makes the live modification a two-minute change.

src/__main__.py
Entry point for python -m src. Parses the three flags, orchestrates, catches top-level errors.
src/models.py
Pydantic models: function definition, parameter, test prompt, output record.
src/io_layer.py
Load + validate the JSON inputs, write the output. All graceful-error logic lives here.
src/vocab.py
Load vocab.json, build id↔string maps, implement byte-level decoding.
src/constraints.py
The validators — name trie, number FSM, string FSM, boolean set. "Which tokens are legal now" + "advance state."
src/decoder.py
The generation loop: append forced tokens silently; at decisions mask with −∞, argmax, advance.
src/pipeline.py
Per prompt: build context, run stage 1 (name), run stage 2 (params), assemble the record.

The seven-day plan

Every day ends with something you must be able to explain out loud — the defense tests understanding, not just a working binary.

1DAY

Setup & the mental model

Prove the pipeline end-to-end before building anything.

  • H1–2: uv init, add numpy + pydantic, copy llm_sdk/ next to src/, uv sync. Confirm the import works.
  • H3–4: Re-read the subject and SDK source. One-page note: which methods exist, what each returns, what's forbidden.
  • H5–6: Explore the tokenizer by hand — encode strings, decode single ids, find Ġ yourself, watch fn_add_numbers split into pieces.
smoke_test.py — the one that must pass first
import numpy as np
from llm_sdk import Small_LLM_Model

model = Small_LLM_Model()
ids = model.encode("The capital of France is")[0].tolist()
logits = model.get_logits_from_input_ids(ids)   # ~151936 floats
print(len(logits), repr(model.decode([int(np.argmax(logits))])))

2DAY

Data models, I/O & error handling

Make every failure a clean message, never a stack trace.

  • H1–3: Pydantic models for both input files and the output record. Load the real files through them.
  • H4–6: I/O layer with full error handling — missing file, invalid JSON, empty array, wrong shape. Deliberately break each and confirm a clean message. Add the argparse entry point with the three flags and default paths.

3DAY

The vocabulary map

Answer "what does this token add?" for any id.

  • H1–3: Load vocab.json, build id→string and string→id. Implement byte-level decoding so any id becomes its real characters.
  • H4–6: Precompute the sets you'll query constantly: pure-digit tokens, a single -, tokens containing ", etc. This is your performance foundation.

correction to fold in

Don't special-case Ġ. Byte-level BPE maps all 256 raw bytes to printable stand-ins — Ġ is just the one for the space byte. Build the full 256-entry byte→unicode table and run every token string through it.

If you only handle Ġ, newlines, punctuation and non-ASCII decode wrong silently. Verify on Day 1 by decoding single ids and comparing to the raw vocab string — see the mismatch with your own eyes.

explain

Why you need the vocab file, and how you map a token id to the exact string it contributes.

4DAY

Decoding loop + name selection (Stage 1)

Where "the model chooses" actually happens.

  • H1–2: The loop skeleton — a masked-argmax step at decision points, and a silent "append a forced token" step that skips the model.
  • H3–6: Build the name trie; wire Stage 1: force {"name": ", constrain to the trie until one name is matched, force the closing quote. Confirm "sum of 2 and 3" → fn_add_numbers, "Greet shrek" → fn_greet.
the masking step, in essence
logits = np.asarray(model.get_logits_from_input_ids(ids))
mask = np.full_like(logits, -np.inf)
mask[legal_token_ids] = 0.0          # only tokens the validator allows
next_id = int((logits + mask).argmax())  # model chooses among the legal
ids.append(next_id)

How trie + masking makes the model choose a valid function with no heuristic, and how you only call the model at decisions.

5DAY

Parameter filling (Stage 2)

The hardest day — budget for it to spill.

  • H1–3: Number FSM (optional sign, digits, optional single dot, digits) — force "<param>": then constrain to number tokens. Test 2, 3, 16.
  • H4–6: String FSM — force opening quote, allow content tokens, let the model pick the closing quote. Test reverse/greet and the 3-param regex prompt. Assemble the record, write the file.

correction to fold in · strings

The closing quote must always stay legal. Multi-char tokens like hello" or ay", smuggle structure into content — forbidding any token containing " can leave no legal token when a short string wants to end. Keep the closing-quote token in the legal set every step.

Test the two cases that break it: an empty string "" and a one-character string.

correction to fold in · numbers

Decide how the number ends, and int vs float. The output example uses 2.0 — floats. Pick a rule and justify it in the README.

At a number boundary, the legal set must include the structural next token (, or }) or the value never closes and you loop forever.

explain

The JSON number grammar and string-escaping rules, and how you guarantee the value's type matches the schema.

6DAY

Robustness, edge cases & lint

Prove it's not hardcoded and it's fast enough.

  • H1–2: Full run over all prompts, timed, under 5 minutes. If slow, check you're not calling the model on forced tokens.

  • H5–6: Makefile (install/run/debug/clean/lint/lint-strict). Run flake8 and mypy with the exact flags; add type hints + docstrings until both pass clean.

Rehearse crisp answers

Defense questions & the live modification

Where does constrained decoding happen, and what does −∞ do?

At each step: mask illegal tokens to −∞ so argmax can't pick them.

How does the model choose the function, not your code?

Trie of names + argmax over the allowed name tokens.

Why is your JSON guaranteed valid?

Invalid tokens are unpickable — validity is structural, not probabilistic.

Why not just prompt for JSON?

Unreliable at 0.6B. Prompting buys accuracy; the constraint buys validity.

What if the model tried a letter inside a number?

The number FSM masks it — that token was never legal.

How do you handle a missing / corrupt input file?

Demonstrate it — clean message from the I/O layer, no crash.

the live modification is almost guaranteed

Common asks: add a boolean or integer parameter type and constrain it, rename output keys or add a field, or force a parameter to a fixed value set. If your constraints live in one module keyed by type, each is a few-minute change. Practise adding a boolean constraint on Day 7 so nothing surprises you.

These cost people points

Traps to avoid

✕

Calling the model on forced tokens. Wastes the 5-minute budget. Only call get_logits at true decisions.

✕

Forgetting byte-level decoding. Comparing raw vocab strings makes matching silently wrong around spaces.

✕

Tokens crossing a boundary. A token can hold content + closing quote. Forbid quote/backslash in content; end the quote as its own step.

✕

Hardcoding to the sample data. The reviewer swaps files. Everything derives from the loaded definitions.

✕

Committing data/output/. Explicitly forbidden — .gitignore it.

✕

Using a private SDK attribute. Instant problem. Public methods only.

The one line that ties it together

Structure from the constraint, intelligence from the model

The prompt gives the model context so its legal choices are the right ones — that's your 90% accuracy. The mask makes every invalid token unpickable — that's your 100% validity. Both matter, and they're different jobs. Say that clearly in the defense and most other questions answer themselves.
